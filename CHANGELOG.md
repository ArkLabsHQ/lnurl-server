and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

### Added
- **Token deposits through FixedFloat (mainnet only)** — with `FIXEDFLOAT_API_KEY` and `FIXEDFLOAT_API_SECRET` set, an address with an Arkade identity advertises one `paymentOptions` entry per stablecoin network (`ff-usdtarbitrum`, `ff-usdcsol`, `ff-usdttrc`, … — USDT and USDC on Ethereum, Arbitrum, Base, Optimism, Polygon, Avalanche, Solana and Tron), each with `type` set to its CAIP-2 namespace, a CAIP-19 `asset`, a `unit` naming a `units[]` entry, and `provider: "FixedFloat"`. The callback creates the corridor swap's hold invoice and a fixed-rate FixedFloat order paying it, and answers the deposit address, an EIP-681 or Solana Pay `paymentURI` (none on Tron), and a `paymentQuote` in the token's base units whose `expiresAt` is the payer's deadline: the earlier of FixedFloat's deadline and the corridor invoice's less `FIXEDFLOAT_SETTLE_MARGIN_SECONDS` (600 s), refused when that leaves under `FIXEDFLOAT_MIN_PAY_WINDOW_SECONDS` (300 s). There is no top-level `expiresAt` on these answers. Settlement is the corridor's alone; `verify` then reports the payer's deposit txid as `paymentReference`. The server never holds or refunds the payer's tokens: a late or wrong deposit is resolved with FixedFloat. **Known risk:** FixedFloat may keep an order open past our deadline, and a payer who deposits in that gap may find the invoice dead and is not paid out; FixedFloat then holds the tokens in its emergency/refund flow. Expired orders stay watched until the TTL, so such a deposit is logged and shown in the admin view. It refuses to start with FixedFloat keys on any network but `bitcoin`, without a file-backed `DB_PATH`, or without offline receive. Every FixedFloat call shares one budget kept 25 units under FixedFloat's 250 a minute. The callback answers 429 past it, past `FIXEDFLOAT_ORDERS_PER_IP` token callbacks from one IP (10 per 10 minutes), past `FIXEDFLOAT_MAX_OPEN_ORDERS_PER_ADDRESS` unfunded orders for one receiver (5), or past `FIXEDFLOAT_MAX_OPEN_ORDERS` in all (20). Each token callback also spends one of the 30 callbacks a minute per IP that the offline Lightning and Arkade destination callbacks share, a limit with no setting, so a burst of them can refuse the same IP's other callbacks for the rest of that minute. After an HTTP 429 from FixedFloat, or five errors in a row, all FixedFloat calls pause for two minutes and the options read `available: false`. Two unroutable-invoice answers (304) in a row close one receiver's token callbacks for ten minutes. Migration 18 adds the `ff_orders` table; the admin rails and settlements views show the rail and each order (never its token).
- **`FIXEDFLOAT_SIMULATE=true`** — an in-process stand-in for test networks (refused on `bitcoin` and with real keys) that answers the same shapes under `ffsim-` ids, `provider: "Simulated"`, on testnet chains, so wallet and checkout UIs can be exercised without real tokens. It takes no deposit.
- **`@arkade-os/lnurl-client` 0.5.0: token options** — `PaymentOption` gains `asset`, `unit` and `provider`; a destination result now carries `paymentURI` (always sent, previously dropped), `paymentQuote`, `paymentDestinationTag`, `expiresAt` and `provider`. `tokenOptions(payRequest)` parses token options exactly as the BTCPay LNURLVerify plugin does, and `requestInvoice` on one checks the answer as the plugin does: the option asked for, an address on the token's chain, and a whole amount of the token.
- **The admin Settlements view links each destination to its explorer and copies it whole on click** — an Arkade destination opens in the Arkade explorer and an on-chain one in mempool, for the network solver discovery reports (no link while discovery is off). Clicking the shortened value copies the full destination, or a Lightning row's payment hash.
- **`verifiable` on every advertised payment option** — whether that option's callback answers carry a LUD-21 `verify` URL, proposed for LUD-XX (lnurl/luds#303). Until now a payer that must detect settlement, such as a merchant backend, learnt that only by requesting a destination, and lnurl-server's onchain option never has one: every checkout cost a refused request, a settlement row and a slot of the per-IP destination budget. Lightning is `true`; arkade is `true` only while per-payment covenant destinations serve it, since the static-address fallback identifies no payment; onchain is `false`. An address served without server caps states nothing, because absent means unknown. `@arkade-os/lnurl-client` 0.4.5 types it as `PaymentOption.verifiable`.
- **`lnurlQuoteMeta(quote)` and the `LnurlQuoteMeta` type** (`@arkade-os/lnurl-client/arkade`) — what an lnurl rail records on its quote (`target`, `via`, `verify`, `verifyBatch`), readable without casting `quote.meta.lnurl`. Undefined for a quote no lnurl rail made.
- **`SentPayment.verify` / `verifyBatch`** — the receiver-confirmation URLs a send's quote carried, so an app can resume a confirmation that was still pending when it closed.
- **`CALLBACK_RATE_LIMIT_PER_MINUTE`** — the per-IP budget for Lightning-address callbacks served without a live wallet session (offline-swap quotes and destinations), hard-coded at 30 a minute until now. Defaults to 30.
- **`TRUSTED_FORWARDERS`: per-IP limits apply per payer behind a server that forwards its payers' IPs** — a server that calls LNURL callbacks for its payers, such as BTCPay Server, reaches lnurl-server from one address, so all of its checkouts shared one per-IP budget and a busy merchant was throttled on every rail. `TRUSTED_FORWARDERS` lists IPs and CIDRs, IPv4 or IPv6, whose `X-Forwarded-For` is believed at any hop on top of the `TRUST_PROXY` hops, so each payer a listed forwarder relays is limited as itself. Anyone else's `X-Forwarded-For` is ignored as before; a malformed entry, or a `/0`, refuses to start. Empty by default.

### Changed
- **`@arkade-os/sdk` 0.5.0-rc.17 and `@arkade-os/swap` 0.1.0-rc.20 — a one-way upgrade** — on its first start, 0.5 rebuilds the SDK's `ark_vtxos` table in this service's database: it adds `is_swept`, `is_preconfirmed`, `commitment_txids_json`, `expires_at` and `expires_at_height`, fills them from the old `virtual_status_json` column, and drops that column. A 0.4 build can no longer read the database afterwards — every VTXO read and write fails, and with covenant destinations on it refuses to boot — so there is no rollback: recovery is fix-forward. `ark_contracts` is untouched. Checked against a database written by 0.4.77 the way this service writes it (covenant destinations in every watch state, including pre-versioning v1 rows; swap lockups; spent, unspent, swept and preconfirmed VTXOs), 0.5 passed 86 of 87 forward checks: every contract row is byte-identical after the upgrade, every covenant and lockup rebuilds its script and address from its stored params, and every VTXO reads back as 0.4.77 stored it. The one miss was the checker's, not the data's: a pre-versioning covenant row gains `version: "1"` when re-serialized, as it always has. The swap package moved its corridor API to `@arkade-os/swap/protocol` and stopped exporting the receive-window gate; the server now runs the same gate through the published `verifyReceiveWindow` from `@arkade-os/swap/advanced`, so a quote whose pay deadline has passed, or whose refund opens within 30 minutes of it, is still refused before its invoice is handed out. The `@noble/*` and `@scure/btc-signer` pins, the client's included, move to the versions the SDK pins, so each is installed once.
- **`paymentQuote.fees` entries are `{ name, amount: { amount, unit } }`** — the shape `@arkade-os/lnurl-client` always read. The server's `QuoteProvider` type and its OpenAPI described `{ amount, unit, description }`, which nothing produced.
- **Covenant destinations stop being watched once this service is finished with them** — a per-payment destination is registered with the SDK as `awaiting-funds`, which the contract manager demotes once a VTXO lands at it. A destination nobody ever paid has no such moment, so it stayed subscribed for the life of the process and the watch set grew with every invoice ever handed out rather than with the payments still in play. Measured at 10,000 dead destinations: 10,000 scripts in the subscription arkd is asked for and an 8.9s restart, against 5 scripts and 1.2s after. A retirement loop now moves a destination to the SDK's `retained` watch state once its sweep is recorded, or, if it was never paid, as soon as it leaves `DESTINATION_WATCH_MS`. The two halves answer to different clocks on purpose: a settled destination stays watched however long its sweep takes, because money that arrived must always reach the user, while an unpaid one is watched only as long as a payment there could still settle — sweeping past that point would move funds `verify` goes on reporting as unpaid. Nothing is deleted: the row still answers reads, still annotates its VTXOs, and still holds the preimage its sweep leaf needs. A payment arriving at a retired destination stays recoverable by the user through the covenant's other two leaves, and was already unattributable once past `DESTINATION_WATCH_MS`. The sweeper and the watcher's catch-up scope their passes to the same set, so neither costs an indexer round trip per dead destination. `pnpm tsx scripts/probe-watchset.ts` reports the numbers.
- **Offline-receive lockups stop being watched once their swap is done** — `registerLockupContract` writes no `watch` state, which the SDK reads as `watched` and never demotes, so every offline Lightning invoice request — every checkout against a receiver who is away — left a lockup script subscribed for the life of the process, unpaid, settled and claimed alike. The retirement loop now covers them too: a lockup is watched while its swap is unsettled and inside the window the settlement poller works, which is the same horizon `listPending` already used, so retirement never outlives an attempt to claim. Past it the poller has stopped trying and the solver reclaims its own lockup through the covenant's refund path, so there is nothing left for this service to watch. Measured across a restart with 155 payments on each rail: 310 scripts in the subscription before, 10 after, with all 310 contract rows kept — a claim rebuilds its covenant from the stored params. The loop also follows the contract manager rather than the covenant rail, so a deployment running offline receive without per-payment destinations gets it as well. Migration 19 adds the partial index both the offline poller's pending-swap read and the new lockup scope need: migration 4's keys the same rows by `swap_id`, so it holds every never-paid swap forever and a `created_at` range over it depended on the planner's statistics — 103µs to 60µs at 50,000 rows without `ANALYZE`, 314µs to 66µs with it, and no longer falling back to an index spanning every settlement row. It is a new version rather than an edit to 17, which has already shipped and run.
- **Three settlements reads no longer scan the table** — migration 17 adds a partial index for each: the covenant scope every worker pass reads, as two indexed halves rather than one `OR` that fell back to scanning every never-paid destination (15.8ms to 0.09ms at 50,000 rows), the payment-reference check a static-rail pass makes once per candidate VTXO (5.6ms to 0.02ms), and the pending-destination read the watched-script resync makes every second (19.2ms to 0.09ms). Each index holds only the rows its query can return, so the cost tracks the payments still open rather than the whole watch window. The migration runner now applies any version it has no record of, rather than everything above the highest one applied: with two branches numbering in parallel, whichever merged second would otherwise have been skipped for good on every database that had already reached the other's version. Merge order no longer matters.
- **Four more reads stop walking rows they only throw away** — node:sqlite is synchronous, so each one held up every request in the process for as long as it ran. The offline poller's pending-swap read lacked the `swap_id IS NOT NULL` that migration 19's index needs, so on every pass it walked every settlement of the last 24 hours, on every rail (504ms to 0.9ms at 50,000 settlements, 7.1s to 19ms at 500,000). The covenant watcher and sweeper named the contract type beside the active scripts, and with three or more scripts SQLite answered that from the type index, reading every covenant destination ever issued (44ms to 0.15ms at 50,000 contracts, 731ms to 0.27ms at 500,000); the scope now names the scripts alone, the table's primary key, and the type is checked in code. The arkade watcher's every-second read returned every unpaid destination of the seven-day window, covenant and onchain ones included, only for the watcher to drop them; it now returns the static-address ones it keeps, from migration 20's partial index (510ms to 0.6ms at 50,000 unpaid covenant destinations, 8.3s to 0.5ms at 500,000). The admin bulk reconcile built a row for every address to keep 200, and the filter and the cap are now part of the query (856ms to 25ms at 50,000 addresses, 12.6s to 129ms at 500,000).

### Removed
- Removed the unused `@noble/ciphers` dependency.

### Fixed
- **`@arkade-os/lnurl-client` 0.5.2: a verify answer can be held to the payment it was issued for** — the preimage check proved only that a settled answer opened its own `pr`, so a verify endpoint could answer for an invoice it had already settled, preimage and all, or with a destination status, and `pollVerify` resolved settled. `pollVerify(url, { expect })` now fails with `LnurlError` on an answer about any other payment: a different payment hash, a destination status for an invoice, or another rail or destination. `expect` takes the callback's answer as it came; lnurl rails record it on their quotes as `lnurlQuoteMeta(quote).expect`, and `verifyStatusIsFor(status, expect)` is the same check for batched and streamed answers. The demo wallet passes it on every confirmation path. Without `expect` nothing changes.
- **`@arkade-os/lnurl-client` 0.5.2: a session's SSE frames stop at 1 MiB** — the parser kept everything after the last blank line, so a stream that never finished a frame grew the client's buffer for as long as it ran. An unterminated frame past 1 MiB now fails the stream with `LnurlTransportError` and cancels the body.
- **A stale solver registry no longer hides a card the operator pins locally** — discovery ignores a registry whose index is over seven days old, but it dropped that registry's markets only after `discover()` had collapsed identical markets into one copy, and it keeps the registry's. Pinning the very card a stale registry lists, through `SOLVER_CARDS_FILE` or `/admin/api/solver-cards`, therefore served nothing: on mutinynet, whose published index is 20 days old, offline receive stayed down with `/readyz` reporting "no usable lightning-receive solver cards" while the admin API called the pasted card `active`. Stale registries are now left out before the copies are collapsed, so the local card serves the market, as does a fresh registry listing the same one.
- **A payment that settles or is paid out behind a newer one now reaches its owner's wallet** — `GET /lnurl/address/:handle/payments` paged on `created_at`, so once a newer payment existed, a wallet's cursor had moved past the older row for good. Its settlement, or the sweep txid a covenant payment records later, never reached the wallet, and the receive stayed a plain "Received" in its history. Settlements now carry `updated_at`, stamped on every write, and the route lists rows least recently changed first with `nextSince` on that column, so a row that changes is listed again. Migration 16 adds the column and backfills it from `settled_at`, else `created_at`. A cursor a client already holds still works: no row's `updated_at` is below its `created_at`.
- **`@arkade-os/lnurl-client` pays a nameless receiver on every rail it advertises** — the server serves a nameless receiver's session LNURL as its address, `paymentOptions` and units included, but the client keyed its rail guards off the URL's shape: `requestInvoice` refused a `paymentOption` or `unit` on any session payRequest, and the lnurl rails offered only Lightning there. A wallet paying a nameless receiver never reached its Arkade leg, and the receiver's own wallet could not ask for an Arkade or on-chain destination. The guards now key off what the payRequest advertises, so a live session, which advertises nothing, is still refused. `@arkade-os/lnurl-client` 0.4.6.
- **The demo wallet's Send takes the amount a pasted payment request asks for** — pasting a BIP321 URI with `amount=` (for example a merchant's unified checkout QR) left the amount field at its previous value. The router sends an explicit amount over the request's own, so paying without noticing underpaid the request. The field is now filled from the URI's `amount=` when one is present, else from its invoice's amount, bare or inside the URI, and is left alone for a target naming neither.
- **A unified BIP21 keeps its Lightning leg when its invoice costs more than `amount=`** — a swap-backed receiver's QR prices the invoice above `amount=` by its swap fee (6002 sats against 5936, say), and `solverLightningRail` drops itself for any requested amount but the invoice's. With the Send amount now filled from `amount=`, pasting such a QR offered only `ark` and `onchain`. `arkadePaymentRouter` now hands the lightning rail the request without an amount that only restates `amount=`, letting the invoice price its own leg; an amount the URI does not name still drops it. Ships in `@arkade-os/lnurl-client` 0.4.7.
- **Covenant destinations refuse to start with a recovery delay shorter than arkd's unilateral exit delay** — `OFFLINE_COVENANT_RECOVERY_DELAY_SECONDS` was checked only for being a positive multiple of 512. Below arkd's `unilateralExitDelay`, arkd refuses every off-chain spend of the covenant address ("exit delay is too short"), the server's own sweep included, so the arkade rail would stall silently while payers kept funding addresses the server could not sweep. Boot now compares the setting with the value arkd advertises and refuses to start below it. The default (86,528 s) clears mutinynet's 2,048 s.
- **An offline receive settles on covclaimd's claim, not on the catch-up poll** — the lockup watcher ran a settlement pass only when the solver funded a lockup, and on funding alone the solver still reports the swap unsettled, so settlement waited for the 15s catch-up. The watcher now also runs a pass when a pending swap's lockup is spent, then re-asks at 1s and 3s, since the solver settles a moment after the claim. A payer's LUD-21 `verify` now sees `settled` within seconds of the claim instead of on the next catch-up.
- **Admin routes refuse a path id that is not a positive integer, and a status change for a missing address is a 404** — `Number(req.params.id)` turned `abc` into `NaN`, which the driver matched against nothing, and `PATCH /admin/api/addresses/:id` answered `{ ok: true }` for an id that did not exist, confirming a change that never happened. Every admin `:id` route now answers 400 for a malformed id, and the status change checks the address exists, as the rail-policy route beside it already did.
- **A wallet's invoice rejection must be short text** — `POST /lnurl/session/:id/invoice` relayed `error` to the payer's wallet whatever its type or length. It is now refused with 400 unless it is a string of at most 500 characters.
- **A callback amount must be written as a plain integer** — both LNURL-pay callbacks read `?amount=` with `Number()`, which also takes `1e6`, `0x3e8`, ` 1000 ` and `1000.0`. They now accept only an optionally signed run of digits, so a non-positive amount still gets the range message it always did. The client's local check had folded "not an integer" into the range message as "Amount must be an integer between…", which no longer matched the server's wording; the two are separate again.
- **A failing background pass no longer takes the process down** — the covenant sweeper, the offline settlement poller and the Arkade watcher ran each pass as `void pass().finally(schedule)`, which schedules the next pass but lets the rejection escape; nothing awaited it, so Node exited on the `unhandledRejection`. A terminal error from the contract manager in the sweep was enough, and a persistent one meant a restart loop that dropped every SSE session each time. All four loops now share one `startCatchUpLoop` that reports a failed pass and carries on, as the covenant watcher already did.
- **An unexpected error no longer answers with its stack trace** — no route had an error handler, so anything a handler did not catch reached Express's default, which renders `err.stack` as HTML whenever `NODE_ENV` is not `production`, and neither the Dockerfile nor the compose file sets it. Routes now throw typed errors (`LnurlError` for LUD-06 bodies, `BadRequest`/`NotFound`/… for the REST API) answered by one handler per app; anything else is logged with its request id and answered `500 {"error":"Internal server error"}`. Malformed and oversized JSON bodies are now answered as JSON too.
- **Odd-length tokens no longer share a session with their even-length prefix** — `isValidToken` accepted any hex of 32+ characters, and `Buffer.from(hex)` drops a trailing odd nibble, so `T` and `T + "0"` derived the same sessionId. Tokens must now be whole bytes, `POST /lnurl/session` uses the same check instead of its own regex, and `deriveSessionId` refuses an invalid token rather than truncating it.
- **A claim whose identity bind failed can be retried** — `claim()` registers the address and then binds the wallet's Arkade identity, so a failure in the second call left a registered row with no identity, and the same wallet re-claiming its own name got `409 taken`: locked out of a name only it owned, and stuck advertising no `paymentOptions`. `POST /lnurl/address` with a `username` now returns the existing row with `200` (the status a repeated nameless call already used) when the requesting session already owns it, active and named; the bind can then be retried on its own. Ownership is the session id every other owner route checks, so a different session — including one replaying a consumed claim code — still gets `409` and can neither take over nor rebind the row. A revoked row stays `taken`, keeping `DELETE` final, and random allocation is unchanged: a retry there mints a new name.
- **An lnurl rail refuses at quote time a destination its inner rail cannot pay** — `arkRail.quote()` does not re-check its target, so a callback destination it could not parse produced a quote that failed only at send, too late to fall back to the lightning option. The rail now asks the inner rail's `match()` first and throws, so a caller trying rails in order moves on.
- **The client loads under `require()`** — its exports map offered only an `import` condition, so anything loading it through CommonJS (Playwright specs, for one) failed with `No "exports" main defined`. Both entries now also export `default`, which Node's `require(esm)` loads; the package is still ESM-only, as its `@noble` dependencies are.
- **Plain Lightning addresses now route** — a LUD-06/16 payRequest with no `paymentOptions` at all (a non-Arkade server) made both lnurl rails report unavailable, so the SDK router found no route. The lightning rail now reads such a payRequest's top-level `minSendable`/`maxSendable` directly and sends no `paymentOption`.
- **The client refuses an invoice that doesn't match the requested amount** — `requestInvoice` never checked the bolt11 it got back; it now decodes the HRP amount and throws when it's missing, unparseable, or disagrees with the requested amount, including an amountless invoice answering an amounted request.
- **The offline-receive invoice check and the client now ignore a payment-hash field whose length isn't 52, as payers do** — both decoders took the first `p` field whatever its declared `data_length` and always read 52 words out of it, while BOLT11 fixes `p` at 52 and has a reader fail the payment on any other length. An invoice of `[p(length 53, first 52 words = the expected hash), p(length 52, the hash a payer reads)]` therefore passed a check against a hash nobody pays: the offline-receive gate (`verifyReceiveInvoice`) would arm a swap on a solver invoice payable to the solver's own hash, and the client's `verify` would accept a settlement proven with a preimage for a hash the payer never paid. A `p` counts only at length 52 now; the first such one still wins and the rest are skipped.

### Added
- **`lnurlActivityResolver`, `sentActivityResolver` and `mergeSentPayment` move into the client** — the demo wallet's activity resolvers were storage-agnostic already (getter args), so they now ship from `@arkade-os/lnurl-client/arkade` for any Arkade wallet to reuse; the demo imports them instead of keeping its own copy. The client's `@arkade-os/sdk` peer range widens to `>=0.4.0 || >=0.5.0-rc.0`.
- **verifyBatch: one request, or one stream, for every pending invoice** — implements the proposed LUD in [lnurl/luds#299](https://github.com/lnurl/luds/pull/299). LUD-21 gives one `verify` URL per invoice, so a payer tracking N pending invoices made N requests per poll and waited out the poll interval for every settlement. The callback and `verify` responses now advertise `verifyBatch`; `GET /lnurl/verifyBatch?verify=…&verify=…` answers the whole set, and with `Accept: text/event-stream` it streams the snapshot and then each settlement as it happens, with `?session=…&add=…&remove=…` changing the tracked set without reconnecting. An over-cap request answers `414`, the status the spec tells clients to split on, and the client's `batchVerify` does split. The client's `openVerifyBatchStream` never sent its `verify` set, so against this server every stream was a `400`; it does now, retries without the stream `Accept` on a `406`, and the demo wallet's Receive tab reopens a closed stream with backoff instead of reporting "not settled".
- **Nameless receivers — a stable LNURL with no lightning address** — a session that never picks a name previously answered "no longer active" the moment the wallet closed, because offline receive, rails, covenant destinations and payment sync all hang off an `addresses` row keyed by username. `POST /lnurl/address { token, nameless: true }` (new `session` allocation mode) now creates that row anyway, keyed by the session id itself, and idempotently on repeat. `/lnurl/<sessionId>` and its `/callback` serve it with full parity — offline swap, rails, covenant — through the same path `.well-known` uses, but with no `text/identifier` in its metadata and refused at `.well-known/lnurlp/<sid>` (a hex handle is never a lightning address). Migration 15 adds `addresses.session_lnurl` plus a partial unique index on `(domain_id, session_id)`.
- **In-place upgrade from nameless to named** — `PATCH /lnurl/address/:handle` (owner-authed, `{ username? }`, or `{ username, claimCode }` for a reserved name) gives a nameless row a name without disturbing its Arkade identity, rail policy, or settlement history; the session LNURL keeps paying the same row afterward, and the owner routes (`DELETE`, `/arkade`, `/payments`, `PATCH`) keep answering to the old session id for that row's owner, so a second device still holding the nameless handle does not 404. Upgrading onto a reserved name keeps any rails the operator disabled on the reservation, merged with the nameless row's own. This links the previously-anonymous LNURL to the new name publicly. A wallet that would rather keep them unlinked can call `claim({ username })` instead, at the cost of a separate address counted against the domain's per-wallet limit.
- **`GET /lnurl/domain`** — public capability discovery (`{ domain, allocationModes, usernameRules, requireApiKey }`) so a wallet can build onboarding from what a domain actually allows instead of guessing.
- **Client: `upgradeAddress`, `domainCapabilities`, and `storedPayments({ domain, handle })`** — the low-level counterparts to the two new routes, plus a lookup key that works for a nameless row (whose `lightningAddress` is `null`).
- **The demo wallet exercises every client feature, and shows the call behind each action** — onboarding and "Add a name" offer a chosen name, a random one, just an LNURL, or an operator-reserved name with a claim code, driven by what `GET /lnurl/domain` says the instance allows. Receive keeps every pending invoice on one verifyBatch stream, adding and removing them with `update()`. Each action has a collapsed snippet of the exact client call it makes, and the demo README opens with a map from feature to UI to call.
- **`arkadeLnurl(...)` — the whole receiver in one object, for anyone holding an SDK wallet** — the client package was a faithful protocol surface that left every consumer to wire the same five things: derive the token with ECDSA pinned, register the address, bind the identity, drive the sync loop, register the LNURL rails. The demo wallet's copy of that wiring ran to 250 lines, and called `deriveToken` twice in one function because nothing memoised it — two extra signatures per boot, and free to get wrong. `arkadeLnurl({ wallet, baseUrl, store })` takes `wallet.identity` for signing and exposes `token`, `owned`, `claim`, `lightningAddress`, `lnurl`, `payRequest`, `payments`, `sync`, `router` and `options`. `claim` does both halves that matter — the name and the identity bind, without which the address advertises no `paymentOptions` at all — and carries the boarding address so the onchain rail exists from the first payRequest. The domain defaults to `baseUrl`'s hostname because a LUD-16 domain cannot carry a port, and `payRequest` addresses its own LNURL through `baseUrl` for the same reason, which is what lets a server on a port resolve at all.
- **The facade takes an identity where there is no wallet** — consuming it found the gap: the demo wallet's own tests hold a `MnemonicIdentity` and an address, never a `Wallet`, so a wallet-only signature was unusable in exactly the place it most needed proving. `arkadeLnurl` now takes either `{ wallet }` or `{ identity, arkadeAddress, boardingAddress? }`, discriminated so the compiler picks one. Receiving needs only a signer; spending the wallet's own coins needs the wallet, so `router()` and `options()` say that rather than failing somewhere obscure. The demo wallet's `lnurl.ts` goes from 159 lines to 21, and with `payment-store.ts` and `router.ts` that is 214 lines of glue deleted for a package the consumer already had.
- **`arkadePaymentRouter(...)` and `browserPaymentStore()`** — paying is not receiving, so the router is available without an address of your own: it returns the SDK router with the LNURL rails registered, which is what makes `route()` accept a Lightning address rather than throw `no rail for`. `browserPaymentStore()` is a `localStorage` `PaymentSyncStore` — enough for a demo and wrong past it, which the README now says in place of claiming the package ships no storage at all. The demo wallet drops its own copies of both: `payment-store.ts` is gone, and `router.ts` goes from 33 lines to 12.

### Changed

### Security
- **32-hex usernames are reserved wherever a name is chosen** — self, random and reserve modes now refuse `^[0-9a-f]{32}$`. Without it, a name freed by an upgrade (or picked coincidentally) could collide with a session id still serving as someone else's `/lnurl/<sid>`, letting a new lightning address silently shadow an existing receiver. Existing rows that already hold a hex name are left alone.
- **The client no longer takes a verify response's word for settlement** — a settled bolt11 status is accepted only when `SHA256(preimage)` equals the payment hash decoded from its `pr`; a mismatch, or a `pr` that cannot be decoded, is rejected (`pollVerify`) or becomes that entry's error (`batchVerify`). The LUD requires it, and nothing checked it before, including `pollVerify`.

The lightning rails are untouched: they carry millisats natively and a sub-sat minimum is legal there.
- **The funded-restart release gate failed in setup rather than in a test** — `fundSolverFloat` retried only "No inputs found", so a `DigestMismatchError` (whose own message asks for the request to be rebuilt under refreshed server info) or an input still held by a prior attempt's intent aborted the run and skipped every test behind it. Those races are now classified by a named predicate rather than a string match inside the loop, and the helper judges itself on what it is for: retries exhausted but spendable value present means the float is funded.
- **Self-claim refused every multi-output lockup, and the money was lost** — the claim skipped any lockup that was not exactly one spendable VTXO, reporting it `unfunded` forever. A solver that funds piecemeal is a documented state of the corridor, and nothing else recovers from it: every non-claim leaf of this covenant belongs to the solver, so an unclaimed lockup is reclaimed at `refund_locktime` and the payer refunded, leaving the receiver with nothing. The claim now spends every live output in one transaction — one payout per input, in input order, because the covenant checks `output[i]` against `input[i]` — with the emulator packet carrying an entry per input and the extension output after them all. The value gate becomes a sum over those outputs rather than a single outpoint, which is safe precisely because the same transaction spends all of them; a short lockup is still refused as `underfunded` rather than revealing the preimage for less than the quote.
- **Nothing stopped a claim being pushed after the solver's refund deadline** — the request-time gate already refused a quote whose claim window was too short, but no later check existed, so the poller retried a claim indefinitely, including inside the window the solver may reclaim in. Publishing the preimage there risks losing the race and giving the secret away for nothing. The claim now refuses once the deadline has passed, reported as its own `expired` outcome and logged at error level, because that one means the payment is gone rather than merely late. The deadline needs no new field or migration: it is already inside the persisted covenant parameters, so swaps quoted before this change are gated too. A block-height-typed locktime is not wall clock and cannot be compared to one, so the gate arms only above the BIP-65 threshold and otherwise leaves behaviour exactly as it was.
- **A settled payment could stay pending in a wallet forever** — `syncPayments` persisted the newest row's `createdAt` as its cursor, but `settled` mutates after a row is created, so once any newer payment existed an older pending row was never re-read; a real capture showed 72 consecutive polls at one unchanged `since` while the UI held a row pending below a newer settled one. The client now persists the oldest row still waiting to settle, reaching one page back at most, and never anchors on an `onchain` destination — nothing server-side watches Bitcoin, so an unsettled row there is terminal, not late. `PaymentSyncStore` is unchanged, but a store that clamps `writeWatermark` to move forward only must stop: the cursor now moves backwards by design.
- **The wallet showed `pending` on a rail whose settlement nothing observes** — an `onchain` record can never leave `settled: false`, so rendering it as pending promised an update that was never coming. Those now read `not tracked`.
- **A covenant destination could stay unsettled forever after a dropped subscription** — settlement runs off the contract manager's `vtxo_received` event plus one catch-up pass at subscribe time, and that pass re-armed itself only from its `catch` branch, so a pass that completed was never scheduled again. The subscription does drop in normal operation (`ContractWatcher subscription disconnected; reconnecting`, observed in a process sixty seconds old), and an event lost to that window was lost permanently. Meanwhile the sweeper — interval-driven, and reading the contract manager rather than the settlement store — kept moving the money, which is the reported symptom exactly: the sweep logs, the recipient's balance rises, and `verify` still answers "not settled". The pass now re-arms whichever way it ends, sized by `OFFLINE_POLL_INTERVAL_MS`, whose documented job is already the backstop for a dropped subscription.
- **The demo wallet's Lightning send rail spoke a framing no solver listens on** — it built `relayTransport`, the dev broker's `{op:"sub"|"event"}` protocol, so a browser could never reach a solver over the swap corridor on mutinynet or a local stack. It failed as an empty market rather than a transport error, which is indistinguishable from "no solver serves this". `connect` now mirrors `src/cli.ts`: `httpTransport` when a solver HTTP URL is configured, otherwise the production `nostrRfqTransport`, imported dynamically so the HTTP path never loads the optional `nostr-tools` peer. The rail no longer needs the wallet identity — relays and solver key come off the rendezvous, and the transport key is deliberately fresh per negotiation.
- **Every solver-lightning send was cancelled while being recorded** — the wallet's `persist` round tripped the swap through `JSON.stringify`, which refuses the BigInt amounts a swap record carries (`TypeError: Do not know how to serialize a BigInt`). It runs before funding and a rejection cancels the send, so this was fatal rather than cosmetic; it was simply unreachable until the transport above worked.
- **The OpenAPI schema omitted `boardingAddress`** — the arkade-identity registration has accepted it since the onchain rail landed, and the server validates it, but the published spec never listed it, so a client generated from it could not register one and the onchain rail was unreachable rather than merely undocumented. `onchain` is now named in the callback's `paymentOption` too, which had described `arkade` as if it were the only destination rail.
- **The admin per-address rail view contradicted the payRequest on the onchain rail** — both admin address views built their `RailAddress` without the address's boarding address, so `effectiveRails` judged `onchain` on a field it was never given. An address advertising `["lightning","arkade","onchain"]` was reported here as having no boarding address at all, on the list and on the per-address rails PATCH alike.

### Added
- **Production runtime and card-only solver discovery** — uses `@arkade-os/solver-discovery` across multiple registries, cached indexes, startup cards, and cards pasted into the admin UI. Direct `SOLVER_URL` / pubkey / relay configuration is removed. Accepted offline swaps atomically persist solver and VHTLC recovery state for restart-safe polling/self-claim. Adds liveness/readiness endpoints, resource caps, redacted structured logs, graceful shutdown, a non-root image, reference Compose deployment, and an operations runbook.
- **Self-claim (`OFFLINE_SELF_CLAIM`, default off)** — the server can push the solver-funded lockup's `nonInteractiveClaim` leaf itself, while the covenant and emulator still constrain payment to the user's registered address. Claims skip underfunded lockups, are safe to retry, and never block status polling. Versioned VHTLC reconstruction data is now persisted atomically with accepted swaps, so self-claim resumes after restart.
- **Per-payment Arkade destinations (`OFFLINE_COVENANT_DESTINATIONS`, default off)** — the `arkade` rail handed every payer the same registered address, so concurrent payments were indistinguishable on the wire and the watcher correlated them by amount and arrival window; two payments of the same amount could not be told apart at all, and a greedy first-fit could let an older, smaller record consume a larger one's payment. With the flag set each callback derives its own address (`src/covenant-destination.ts`) and the script becomes the identifier: a VTXO there belongs to exactly one record, so `src/covenant-watcher.ts` settles it on the contract event instead of guessing (the arrival window, the 15s skew and the oldest-first assignment all drop away; the amount check stays, since an under-payment must not flip `settled`). `src/arkade-watcher.ts` skips these records and keeps correlating the static-address rail only, where amount and arrival time remain all there is. The address is three Taproot leaves — `condition(H(P))` + operator + a cosigner key committing to `enforcePayTo(static address)`; user + operator; and user alone after a CSV (`OFFLINE_COVENANT_RECOVERY_DELAY_SECONDS`, default 86528 — BIP68 counts seconds in 512s units, so 24h exactly is not expressible). Only the first carries `H(P)`, so a fresh preimage moves the address while the covenant bytes stay fixed, and **the preimage is not a secret**: the covenant means anyone holding it can only pay the user, which is why the two recovery leaves are keyed to the user and need neither `P` nor this server. A sweeper (`src/covenant-sweeper.ts`) moves each funded destination on to the static address, so the receiving wallet sees an ordinary arrival and needs to know nothing about the covenant. Costs one extra Arkade transaction per payment and a dependency on the emulator co-signing the sweep; requires `OFFLINE_EMULATOR_URL`, `COVCLAIMD_URL` and `ARK_SERVER_URL`, all checked at startup rather than when a payer is already holding an address. Derivation failure at request time falls back to the static address — ambiguous again for that payment, which beats refusing to be paid. Tracking, watching and spending are the SDK's: the covenant is registered as a contract type (`src/covenant-contract.ts`) so `ContractManager` owns its lifecycle — a subscription instead of a poll, `awaiting-funds` demoting itself once a payment lands, and `getSpendablePaths` choosing the leaf. Adds migration 007 (`covenant_script` with a unique index) as the join key; everything else about a covenant lives in the SDK's own `ark_contracts`.
- **ClaimPacket TLV codec** (`src/claim-packet.ts`) — encode/decode for the Arkade extension packet body covclaimd matches on (type `0x04`; TLVs `0x01` ciphertext, `0x02` arkade_script, `0x03` covclaimd_pub_key), transcribed from covclaimd's `pkg/preimage/packet.go`. Groundwork for the non-interactive claim path in which the funder stamps the packet into the lockup's funding transaction instead of revealing it to covclaimd over HTTP ([arkade-os/intent-solver#46](https://github.com/arkade-os/intent-solver/issues/46)); Wired behind `OFFLINE_STAMP_CLAIM_PACKET` (default off): with it set, the callback sends `0x01` ciphertext + `0x03` covclaimd_pub_key instead of the bare ciphertext, so the solver stamps the packet on chain and the covclaimd is ours to choose rather than something both sides must have been configured with. Off by default because a solver predating that PR forwards the packet as a ciphertext, cannot decrypt it, and the swap funds and refunds.
- **LUD-21 (`verify`)** — LNURL-pay callback responses now carry a `verify` URL, and a new `GET /lnurl/verify/:paymentHash` lets payers poll settlement status (`{ status, settled, preimage, pr }`). Because this server is a relay with no Lightning node, wallets report settlement via the new authenticated `POST /lnurl/session/:id/settled` with `{ preimage }` — the server checks `sha256(preimage)` against a payment hash the session issued (decoded locally from the bolt11, no new dependency) before flipping the record to settled. Settlement records live in a new `settlements` table (migration 003) when `DB_PATH` is set, or in an in-memory store with a `VERIFY_TTL_MS` (default 24h) lifetime otherwise, so a payer can still poll `verify` after the wallet disconnects. Available on both the ephemeral LNURL and the LN-address (LUD-16) flows.
- **Offline receive (opt-in)** — with solver cards plus `COVCLAIMD_URL` and `ARK_SERVER_URL`, an LN address can register an Arkade receive identity and receive while its wallet is offline. The server obtains a Nostr RFQ through the ranked card candidates, returns the verified hold invoice, and tracks the pinned solver through LUD-21 settlement without holding user keys or funds.
- **Payment options (LUD-XX, `paymentOptions`)** — an LN address with a registered Arkade identity now advertises `paymentOptions: [lightning, arkade]` in its LUD-06 `payRequest`. A payer selects a rail with `?paymentOption=<id>`: `lightning` (or absent) keeps the existing BOLT11 / offline-swap flow; `arkade` returns the user's Arkade address as a `paymentDestination` (direct receive, no swap) plus a `verify` URL that reports the non-`pr` LUD-21 shape (`{ settled, paymentOption, paymentDestination, paymentReference }`). Unknown/unavailable options return `{ status: "ERROR", reason: "Unsupported paymentOption" }`. Settlement records carry the option + destination + agreed amount (migration 006, incl. `amount_msat` so the future watcher can correlate observed payments). Because the payer pays the Arkade address directly, the server isn't in the payment path, so arkade `settled` flips only when the server-side Arkade watcher observes the payment — which ships in this same release, below. The resolver is a small registry (`src/payment-options.ts`) so future rails/assets slot in.
- **Payment quote (LUD-XX, `paymentQuote`)** — when a `QuoteProvider` is injected, the LN-address `payRequest` advertises `units` (e.g. USD), and a callback with `?unit=<code>` (optionally `&receiveUnit=`) is quoted: the provider converts the unit amount to the effective msat amount used for the bolt11 / offline swap, and the response echoes `paymentQuote` (`{ requested, payment, receive?, fees? }`). This server has no rate oracle, so without a provider `units` is omitted and any `unit=` request returns `Unsupported unit`. Framework only — real rate sourcing, assets, and swap-backed quotes plug in behind `QuoteProvider` (`src/quote-provider.ts`). Applies to the amount-denominated Lightning path (relay + offline swap); quoting the `arkade` destination rail is a follow-up.
- **Arkade settlement watcher** — when `ARK_SERVER_URL` is set, a background poller watches the Arkade indexer for payments to destination-rail records (`paymentOptions: arkade`) and flips `verify` to `settled: true` with `paymentReference` = the observed Arkade txid. Matching is by destination script + agreed amount (`amount_msat`, never under-paid) + arrival window; each observed VTXO settles at most one record, oldest first. Correlation fuzziness (an unrelated same-amount payment in the same window) is inherent to reference-less address payments and is documented in the README.
- **Solver discovery** — `SOLVER_REGISTRY_URLS`, a startup card file, and admin-pasted cards merge into one atomically refreshed, fee-ranked discovery snapshot with bounded registry caching.
- **Admin settlements view** — `GET /admin/api/settlements` (filter: `settled`, `option`, `limit`) lists LUD-21 settlement records (relay invoices, offline corridor swaps, destination-rail payments) newest-first, never exposing preimages or invoices; plus a Settlements tab in the admin SPA with a 5s live poll.

### Security
- **Patched express's transitive dependencies** — `path-to-regexp` 8.3.0 → 8.4.2 (high severity), `qs` 6.15.0 → 6.16.0, and `body-parser` 2.2.2 → 2.3.0, which between them clear every advisory open against code this server actually ships. Lockfile only: express 5.2.1 is already the newest release, and the ranges it and `router` declare already allowed the patched versions, so nothing in `package.json` changed. The advisories left open after this are all dev-only (`vite`, `postcss`, `nanoid`, `esbuild`, and the `form-data` under `supertest`) and none reach the published image, whose final stage installs `--prod` and copies only `dist`.

## 0.2.0 - 2026-06-04

### Added
- **SQLite persistence** — opt-in via `DB_PATH`; without it the service is fully in-memory as before. Uses Node's built-in `node:sqlite` module.
- **Token storage** — wallet session tokens use AES-256-GCM with a private `TOKEN_ENCRYPTION_KEY`; `ALLOW_INSECURE_TOKEN_STORAGE=1` explicitly selects a source-known fallback key when the operator accepts that it provides no database confidentiality.
- **LN Address (LUD-16)** — `/.well-known/lnurlp/:username` and `/callback` resolution. Host-based multi-domain routing: the `Host` header selects the domain. Returns an error when the wallet's SSE session is offline.
- **Address provisioning** — unified `POST /lnurl/address` supporting self-claim (wallet chooses username), random assignment, and reserved-address claiming via `claimCode`. `GET /lnurl/address` lists own addresses by Bearer token; `DELETE /lnurl/address/:username` revokes an owned address.
- **Per-domain provisioning policies** — `allocationModes` (`self`/`random`/`admin`), `requireApiKey`, `max_per_session`, username length/pattern rules, per-domain or global blacklist, registration rate limit (`REGISTRATION_RATE_LIMIT`).
- **Admin JSON API** on `ADMIN_PORT` (default 3001, bound to `127.0.0.1`): full CRUD for domains, addresses (reserve/mint), API keys, blacklist; read-only view of active sessions.
- **Admin React SPA** served at the admin port root — dashboard, domains, addresses, and API keys tabs.
- **`BOOTSTRAP_DOMAIN`** env var — creates a default domain on first startup if none exist.
- **`TRUST_PROXY`** env var — configures Express `trust proxy` for correct client IPs and origins behind a reverse proxy.
